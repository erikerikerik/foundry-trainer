Major architectural decisions and failed approaches that affect future work. Not a command history.

## 2026-10-28: 0.5.8b worker bin, faithful klein stack, gradient checkpointing (local, no GPU runs)
- **0.5.8b implemented: `src/bin/worker_teardown.rs`.** Parent holds *no CUDA context at all* (NVML only), spawns its own executable with `--child`, waits for exit, sleeps 1 s for the NVML counters, re-reads. Child owns the whole CUDA lifetime, runs the identical 20-step bf16 AdamW burst from `mem_teardown.rs`, and exits without releasing anything by hand — process exit is the thing under test. Same 200 MB gate as 0.5.8 (not loosened), three rounds with a fresh baseline each so an accumulating leak shows as a rising deficit, `RESULT: PASS/FAIL` and exit 1 on FAIL. Owner-run.
- **`throughput.rs` stack is now faithful to klein** (the earlier stack was deliberately pessimistic): `mlp_ratio` 3 → hidden 9216, and **one modulation linear shared by all 25 blocks** instead of one per block. The single-stream block is one fused in-projection 3072→27648 (q,k,v of 3072 each, then a SwiGLU gate and up of 9216 each) and one fused out-projection 12288→3072 taking the attention output joined with the activated MLP. Stack total 396·dim² ≈ 3.74B params, against ~5.9B before and ~4B real. The widths the plan depends on are pinned by a `const _: () = assert!(...)`, so a future edit that breaks 9216/27648/12288 fails to compile.
- **Assumptions recorded in the bin header** (they are assumptions, not readings): gating the two branches before the concat is identical to gating the projection halves after it (linearity), but *which* chunk of the fused in-projection is q/k/v/gate/up is unreferenced. `docs/RESEARCH.md` has no section 3.1 — the klein config is section 2 and section 3 is "Not yet researched" — and LoRA target modules/rank are listed there as an open item, so rank 4 sits on the fused single-stream in/out projections plus double `img.to_q`/`to_v` as the pattern the fused layout implies, not a confirmed reference config. Biases are zero only because the lib's `linear` requires a bias key.
- **OOM reporting fixed (0.5.9 follow-up):** the peak-VRAM line now prints *before* the error propagates — an OOM run is exactly the case where the peak reading is the interesting number — and errors are tagged `died in forward`, `died in backward (loss)`, `died in backward (recomputing stage k)` or `died in backward (stage k)`, so each config reports which phase it died in.
- **Per-block gradient checkpointing: `lib::checkpointed_backward` + `Stage`.** Forward runs every stage graph-free (LoRA factors passed in detached — same storage, so still current values — so no `BackpropOp` is recorded and each stage's intermediates are freed on return); only stage *inputs* are retained. Backward walks stages in reverse, makes their saved inputs variable leaves, rebuilds the graph with the **same** `run` closure (so "gradients unchanged" is a real claim, not a different graph), and injects the upstream gradient with the seed trick proven in 0.5.4 (`sum(out·upstream)`, whose backward hands `upstream` to the graph untouched). Behind `--checkpoint` in `throughput` (25 stages) and `block_backward` (2 stages).
- **Proof the gradients are unchanged — `tests/checkpoint_grads.rs`, CPU + fp32 fixture, no GPU run:** all 8 gradients (6 LoRA A/B + `grad/inputs/img` + `grad/inputs/txt`) are **bit-identical** between full-graph and checkpointed backward (rel L2 0.000e0, cos 1.000000), and both agree with the PyTorch fixture to worst rel L2 1.34e-3 / cos ≥ 0.999999 — inside the unchanged 2e-2 / 0.999 gate and well inside the fixture's own 1.2e-2 gradient noise floor. `block_backward --checkpoint` runs the same acceptance on GPU.
- **`tools/fixtures/PROVENANCE.md` now lists the fixture-vs-faithful-layout differences** (separate `to_qkv`/`mlp_gate`/`mlp_up` vs one fused in-projection; no out-projection at all in the fixture; MLP 2·dim vs ratio 3; per-block biased modulation vs one shared bias-free linear; LoRA targets; RoPE theta 10000 vs 2000). **Fixtures were not regenerated** — `gen_block.py` is unchanged and every recorded tensor stays bit-identical. Consequence: the fused in/out-projection and shared-modulation paths have no PyTorch reference, only the throughput run's own forward/backward consistency.
- Local verification: `cargo fmt`, `cargo clippy --all-targets -- -D warnings` clean, `cargo build --release` OK, `cargo test -p foundry-spike` 1 passed (the new CPU test). No GPU program was run — 0.5.8/0.5.8b/0.5.9 measurements stay owner work with Strata unloaded.
- Still unknown until the owner re-runs: whether checkpointing makes 512px (and anything else) fit on the 4090, and what the faithful (smaller) stack costs per step.

## 2026-10-28: spike item 0.5.7 PASS; determinism, 1000-step stability, and a corrected stability criterion
- `stability.rs`: (a) two independent 10-step bf16 runs from fresh fixture loads produce **bit-identical** per-step losses and final LoRA params (compared via `to_bits`; bf16->f32 is injective). (b) 1000 bf16 AdamW steps on fixed fixture data: loss 3.8932 -> 2.1219 in ~17 s, every loss and parameter finite. PASS.
- **Criterion corrected by evidence, not loosened:** my first gate demanded step-to-step rises <= 1e-4; the bf16 run showed isolated rises up to 1.55e-3 (179/999 steps, longest consecutive run 3, clustered where the curve flattens). The fp32 control refuted my "bf16 quantization noise" hypothesis outright — fp32 rises too, and *larger* (max 6.25e-3, 37/999). The rises are ordinary Adam overshoot at lr 1e-3, dtype-independent. The gate now targets what the plan actually accepts ("no drift"): 100-step window means strictly decreasing, longest rise run <= 10, single-step rise <= 1e-2, finite + descending — same gates for bf16 and the fp32 control; both pass. fp32 descends further (3.89 -> 1.90), as expected.
- **Candle fp32 contiguity gotcha:** `to_dtype(X)` on a tensor already in X is a no-op clone that *keeps non-contiguous layout*. In bf16 the F32 casts inside `attn_fwd` accidentally materialized the batch-transposed views; in fp32 the view reached CUDA matmul and was rejected (overlapping batch strides). Fix: `.contiguous()` after the cast — a no-op for the bf16 path; `block_backward` re-run confirms identical 0.5.5 numbers.
- AdamW extracted from `opt_step.rs` into `lib::adamw_step(var, grad, m, v, step, &AdamW{..})`; hyperparameters in a struct (clippy `too_many_arguments`).
- Numerical path A risk is now retired: 0.5.1-0.5.7 all PASS. 0.5.10 records the decision now; 0.5.8/0.5.9 remain owner-run measurements (NVML teardown, real-dim throughput) that the record lists as pending.

## 2026-10-28: spike item 0.5.6 PASS; AdamW on LoRA parameters
- `opt_step.rs`: 10-step training loop mirroring the reference in `gen_block.py` — per step: fresh forward graph at current parameter values (inputs stay plain tensors, the reference detaches them), `loss.backward()`, hand-written bias-corrected AdamW (lr 1e-3, betas 0.9/0.999, eps 1e-8, wd 0), in-place `Var::set` with the bf16 result. LoRA values after steps 1 and 10 vs fixture `opt1/*`/`opt10/*`: worst rel L2 1.18e-2, worst cosine 0.99993 — inside both the 2e-2 acceptance and the fixture's own 1.64e-2 bf16-vs-fp32 noise floor for these tensors. Loss falls monotonically 3.8932 -> 3.8818. PASS on first attempt.
- Optimizer-state dtype decision: moments kept in **fp32** even though params are bf16 (the production choice; PyTorch's reference keeps them in bf16). The fp32 state did not hurt the comparison — it sits below the reference's own precision noise — so no bf16-state fallback was needed. `Var::set` is safe here: the update tensor comes from `to_dtype` (new storage), so candle's "derived from its value" guard does not fire, and the `w`-map entries share storage with the vars, so the next iteration's graph sees the update.
- Path A risk now rests only on 0.5.7 (determinism, 1000-iteration stability).

## 2026-10-28: spike item 0.5.4 PASS; hand-written attention backward
- `attn_backward.rs`: attention as a Candle `CustomOp3` (bf16, CUDA). Forward replays the reference graph; backward is hand-written to mirror PyTorch autograd over that exact graph: dprobs/dV as bf16 matmuls, softmax backward in fp32 (`dscores = p*(dp - sum(dp*p))*scale`), dQ/dK as fp32 matmuls cast back to bf16. Result vs the `grad/attn/*` fixture tensors: cosine 1.000000, worst rel L2 1.4e-6 — far inside the 0.999/2e-2 acceptance and the 1.1e-2 bf16 gradient noise floor. Forward inside the op is bit-identical to the recorded attention output (rel L2 0), proving `cuda_fwd` ran.
- Test harness trick: wrap q/k/v in `Var::from_tensor` (Candle only tracks gradients for variable leaves), then seed the backward with the recorded upstream gradient via `attn.mul(seed)?.sum_all()?` — mul backward hands the seed to the op unchanged. Required extending the fixtures: `attn_in/{double,single}.{q,k,v,attn}` and `grad/attn/*` (via `loss.backward(retain_graph=True)` + `torch.autograd.grad`), 94 -> 110 tensors; no RNG draws changed, all pre-existing tensors bit-identical (block_forward re-run: identical numbers, PASS).
- **Candle 0.11 CustomOp-on-CUDA facts** (verified against source): `storage.rs` `apply_op3` dispatches CUDA storages straight to `cuda_fwd` — no CPU fallback, so a CUDA-used op must implement `cuda_fwd`. `CudaStorage::try_clone` is trait-private (`BackendStorage`), but `candle_core::backend::BackendStorage` is public — import it and `s.try_clone(layout)` materializes any layout into a contiguous slice. Combine with the public `Tensor::from_storage(storage, shape, BackpropOp::none(), false)` to compose ordinary Candle ops inside `cuda_fwd`/`cpu_fwd` instead of writing raw cudarc kernels (Path B not needed for this op). CPU side: `CpuStorage` is `Clone` but cloning ignores the layout — guard with `contiguous_offsets() == Some((0, numel))`.
- Path A status after 0.5.4: Candle autograd + one custom op covers attention end-to-end. Remaining risk moves to 0.5.5 (full-block backward through composed ops) and 0.5.6 (AdamW).

## 2026-10-28: spike item 0.5.3 PASS; Candle-CUDA on MSVC toolchain recipe
- `block_forward.rs` (Candle 0.11 core+nn, `cuda` feature) replays the fixture block pair in bf16 on the 4090: all 17 recorded activations within tolerance, worst rel L2 6.2e-3 (norm1 1.8e-3, q/k ~3.2e-3, attn ~5-6e-3, outputs ~9e-4) vs 2e-2 threshold and 1.64e-2 fixture noise floor. `RESULT: PASS`. Path A (Candle autograd) stays viable; 0.5.4 will add the hand-written attention backward.
- **Toolchain recipe (was 4 failed build attempts):** candle-kernels compiles .cu -> PTX via nvcc at build time, which needs the MSVC developer environment that Git Bash lacks. Fix: `. tools/dev/vcvars-env.sh` before cargo builds — it runs `vcvars64.bat` via a space-free wrapper bat (Git Bash mangles quoted args to cmd), converts PATH through `cygpath -up`, keeps INCLUDE/LIB Windows-format, and exports `CL=/Zc:preprocessor` (CUDA 13.4's CCCL headers `#error` under MSVC's traditional preprocessor; cudaforge has no extra-flags hook, but cl.exe reads `CL` on every invocation, including nvcc's).
- **candle-nn gotcha:** its CUDA fast paths (layer-norm, softmax CustomOps) are gated on candle-nn's OWN `cuda` feature; enabling only candle-core's `cuda` yields runtime `no cuda implementation for layer-norm`.
- **Candle 0.11 API facts** (verified against source): `add/mul/sub/div` require identical shapes — broadcasting needs `broadcast_*`; scalar math via `affine(mul, add)`. CUDA `matmul` rejects batch-transposed views (overlapping batch strides); call `contiguous()` on operands.
- **Golden-test win:** first run showed ~2.5e-1 rel L2 on every adaLN-normed activation while residuals looked fine — the reference feeds `silu(temb)` into the modulation linears, which the Rust port had missed. Plausible-looking residual values would have hidden it; the per-activation comparison caught it immediately.
